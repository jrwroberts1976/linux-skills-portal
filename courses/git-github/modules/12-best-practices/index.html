    Module 12 - Git Best Practices¶

    Best practices are habits that make a repository easier to review, recover and hand over. The goal is not a long rulebook. A professional repository should make the safe path obvious and the history understandable.

    Learning Objectives¶

    • Understand the core concepts in this module.
    • Use the relevant Git/GitHub commands deliberately.
    • Validate repository state before and after a change.
    • Recognise common failure modes and choose a safe recovery path.

    Small coherent commits¶

    Each commit should have one purpose. This improves review, rollback, bisecting and history.

    Before committing: 

    git status
git diff
git diff --staged

    If the staged diff contains two unrelated reasons for change, consider splitting it.

    Commit messages¶

    A useful subject is short and specific:

    Add health check to Grafana container
Fix DNS resolver validation
Document Proxmox backup recovery

    For larger changes, the commit body can explain why the change was needed and any non-obvious trade-off.

    README and operational documentation¶

    A new engineer should be able to discover: - repository purpose - prerequisites - how to validate/test - how changes reach an environment - where secrets come from - recovery or rollback expectations - ownership/contact information where appropriate

    Documentation that cannot survive repository handover is a support risk.

    Protected default branch¶

    For important repositories, protect the default branch with pull requests and relevant required checks. Avoid routine direct pushes by administrators because bypass culture undermines the value of controls.

    Repository security¶

    Use least-privilege access and remove stale collaborators. Enable secret scanning/dependency/security features where available and appropriate. Do not expose secrets in examples, screenshots, logs or Actions output.

    Consider CODEOWNERS when specific paths require specialist review, such as networking, security or production deployment files.

    Signed commits and tags¶

    Cryptographic signing can provide stronger evidence about who created a commit or tag. Whether to require signing depends on the organisation's threat model and operational overhead. It is a useful control, not a replacement for code review.

    Repository hygiene¶

    Keep generated output, caches and temporary files out of source control unless they are deliberately required artefacts. Remove merged branches, prune stale remote references and periodically review repository settings and workflows.

    Recovery mindset¶

    Before a risky history operation, identify: - what commit/reference you are on - whether the history is shared - whether uncommitted changes exist - how you can recover

    Commands such as git status, git log --graph --all and git reflog should come before destructive guesses.

    Command Walkthrough¶

    git status
git diff --staged
git log --oneline --graph --decorate -15
git branch -vv
git remote -v
git ls-files

    Run these commands in a disposable repository and read the output after each step. The output is part of the lesson; do not treat commands as a script to paste without understanding.

    Practical Lab¶

    Audit one of your own repositories: 1. Read the README as if you had never seen the project. 2. Review the last ten commit messages. 3. Check the default branch protections/rules. 4. Review tracked files for generated output or secrets risk. 5. Check stale branches. 6. Confirm how validation runs before merge. 7. Add a short REPOSITORY-STANDARDS.md or improve existing documentation with the standards you actually want to follow. 8. Open the change through the normal branch and PR workflow.

    Common Mistakes¶

    • Creating a huge standards document nobody follows.
    • Protecting branches without ensuring required checks are reliable.
    • Putting sensitive values into examples because they are 'only documentation'.
    • Cleaning history with destructive commands when a normal revert would be safer.

    Knowledge Check¶

    1. What makes a commit useful to a future reviewer?
    2. Which controls would you apply to an important default branch?
    3. When might CODEOWNERS help?
    4. What should you check before rewriting history?

    Module Completion Criteria¶

    • [ ] I can explain the module without reading the command list.
    • [ ] I completed the practical lab in a disposable repository.
    • [ ] I inspected the resulting history/state.
    • [ ] I can explain one safe recovery action.
